# HumID 3.0 — the app, rebuilt

**Status: 3.0.0, October 2026.** The app in `apps/mobile` was rebuilt from the ground up
around three things the 2.x app had grown away from: one kernel of small modules instead
of a 2 100-line controller, the official brand carried as meaning rather than decoration,
and a first paint that carries nothing it doesn't need. The protocol (HTP/1), the envelope
format, the services and the packages are unchanged except where this document says so;
3.0 phones talk to 2.x servers.

This document is the spec: what 3.0 is, what changed and why, what it costs, and where it
grows next. The reviews it answers are summarised in §7.

## 1. Shape

```
apps/mobile/src
  main.jsx              one column · one view · one pushed screen · one sheet (≈ 70 lines)
  brand/                the brand, as code: tokens.css · base.css · flows.css · shell.css
                        mark.jsx (the official mark, vector) · icons.jsx · logo-data.js
  ui/                   kit.jsx (Sheet, Pushed, Row, Banner, Confirm, Toggle, Interrupt …)
                        codes.jsx (recovery cards, match codes, QR, chip access) · shell.jsx · format.js
  core/                 the kernel. Screens import ONLY core/index.js (tests/ia.test.js)
    index.js            the public surface: every verb the app can do, one list
    runtime.js          R: store, api, session keys, epoch · state.js: the signals screens read
    session.js          boot · connect · unlock · lock · offline copy · preferences
    interrupt.js        withKeys / withStepUp: one live check, one operation, keys wiped
    enroll.js join.js   Create my HumID · I already have HumID (link, two-proof recovery)
    vault.js            list · seal · open · save · export · rename · pin · decoy · delete
    ledger.js devices.js recovery.js safety.js (duress, Heartbeat) chips.js operators.js
    drafts.js           what survives a lock (UX-17)
    comms/contract.js   the secure-human-communication boundary (§6)
    scan.js analyzer.js scanworker.js docfind.js capture.js … (the document camera)
    guide.js guidecap.js scanjobs.js         the guided scan's maths and still; the clean scan off the main thread (2.2.0)
  screens/
    welcome.jsx lock.jsx vault.jsx          first paint
    create.jsx join.jsx                     onboarding, loaded when chosen
    add/ (index, camera, review, ids, cards, passes)   the Add flow, loaded on "+"
    activity.jsx                            loaded on its tab
    you/ (index = hub, protect, devices, recovery, duress, heartbeat, help, settings, about)
```

**Rules that keep it small.** A screen reads signals and calls kernel verbs; it never holds
a key, talks to the server, or imports another screen's internals. Every sheet and pushed
screen type is rendered by exactly one file. Nothing animates unless the person did
something or a check is running. No `filter`/`backdrop-filter` on anything that scrolls.
Every size is a token or `rem`. The kernel's modules share one object (`R`) and an
`epoch`: `lock()` increments it, and any result that began in an earlier epoch is dropped,
not shown. Every signal in `state.js` is either per-session, put back as it started by
`resetSession()` (lock, erase and reset all call it), or on its `DEVICE_SCOPED` list with a
reason; `tests/state-reset.test.js` fails on a signal that is neither.

## 2. The brand, as meaning

Source of truth: the official HumID mark (the hand with fingerprint tips; amber `#F5A623`
"Hum", mint `#6FE3B4` "ID.", on ink `#0B1410`). `brand/tokens.css` is the one place the
brand lives; no component knows which theme it is in.

| Colour | Means | Where |
|---|---|---|
| **amber** | a human, and a human action in progress | the hand, every button that will run a live check (always with the fingerprint icon), the check overlay while it runs |
| **mint** | verified · sealed · proven | the badge, pills, "Proven by this phone's secure chip", the ring when a check passes |
| **danger** | wrong, or can't be undone | failure banners, Delete, Close & erase |
| neutral | everything else | dismissals are ghost buttons; kinds (ID, card, pass, photo, file) have their own quiet hues, never amber or mint |

Type is the system face (SF, Roboto, Segoe): zero bytes, native rendering, and the OS text
size applies without code. Four in-app steps (100 · 120 · 145 · 175 %) multiply on top of
it. Light theme keeps the same meanings with ink-on-paper values measured at ≥ 4.5:1.

One vocabulary, and *check* means only the biometric: **Heartbeat** (was Check-in),
**match code** (was account check), *seal*, *witnesses*, *recovery card*, *ID chip*,
*your vault server*. The first thing Welcome and Lock say is the thing that makes HumID
different: *no password exists; a living you, proven by your phone's chip, opens it.*

## 3. The journeys (what changed for the person)

- **Welcome · Create · Lock.** The no-password sentence first. The sole-biometric
  confirmation is never a grey button: tapping Create scrolls to and highlights the
  confirmation. The recovery card screen says "Shown once. Write it down now." and can
  print or share the card from a phone. The server-key screen leads with the host and
  hides the key behind "Show its key". A tap on the mark responds at once; a plain click
  unlocks (screen readers, switch control); **duress gestures** are now a triple-tap on the
  mark (default) or a 3-second hold, with a practice mode in Settings that signals nothing.
- **Vault · Add.** 3.0.1: what it is comes first. Add opens "What are you adding?", which
  lists each kind directly (Passport, Driver's license, State ID or ID card, Green card or
  residence permit, Another card, Payment card, Document, Photo, Wallet pass, File; the last
  one used on top), and picking one opens its own camera at once, its readers already loading.
  (3.0.0 was camera first, with the phone's document scanner on Android and its four-point
  outline; that is gone from Add.)
- **The mark and the icon (3.0.1).** Inside the app the mark is the fingerprint again (2.x's
  ridges in the brand's amber to mint, inside 3.0's ring: lock, welcome, the check overlay, the
  empty vault). The peace-sign hand is the logo and the app's launcher icon (`tools/app-icon.mjs`
  draws it from the logo's vector data and runs `tauri icon`; Android gets an adaptive icon on ink).
- **The capture screen (3.1.0).** The frame stays fixed; a lock box inside it follows the document the
  camera sees and settles onto the frame; one instruction and live chips (Framed · Sharp · Steady ·
  Light · Barcode / ID lines) sit right under the frame; a license's barcode and a passport's lines
  are read live, so the photo is taken the moment the details are in; the photo freezes in the frame;
  and the camera says back what it read before moving on, or says plainly what it couldn't read with
  Try again / Keep the photo. A license back held up for the front is kept as the back. Tap to focus.
  `core/capture.js`; details in `docs/ID-SCANNING.md`.
- **Two cameras, one card of words (2.2.0's guided scan, carried into 3.0).** A card, a
  license, an ID card or a passport page is a **guided scan**, like a bank's: a fixed
  outline at the document's real proportions (ID-1 85.6 × 54 mm, ID-3 125 × 88 mm),
  centred, everything outside it dimmed (`--cam-dim`), and plain words for what to change
  (Move closer, Move back a little, Straighten the card, Hold the phone flat, Not sharp yet,
  Too much glare, Too dark, Hold steady, Show the back). Lined up, steady and sharp for
  about 0.6 s, the photo is taken by itself — a full-resolution still where the phone
  offers one (`core/guidecap.js`, checked against the preview's framing or refused), cut
  to the outline — and the barcode or MRZ is read from that still; the round button
  always takes it. The outline never moves. The stream asks for the long side only (1920 px;
  2560 for a passport's small print), never a crop, and asks again with both sizes only if it came back turned. **Anything else** (the Add
  camera, Photo) finds the document by itself and straightens it: that stream is ~1080p,
  asks for the long side only and never a crop, so the camera's whole field of view
  arrives (asking for a width *and* a height makes a browser cut a portrait frame square,
  losing the top and bottom of the page; `tests/browser/photo.mjs` guards it). Both stop
  the track when the app is hidden. After a capture, the review opens before the clean
  scan of a page is made (in the scan worker), the JPEG is encoded while the review is
  read, the sealing arithmetic is warmed on throwaway keys, and the location fix is
  waited for beside the encryption (3 s at most).
  The location stamp is **off by default** per device, explained once, and ~110 m precise
  when on. Back from the picker returns to the review with its text intact. A form, and
  an ID's captured sides, **survive a lock** (`core/drafts.js`: text 10 min, images 2 min,
  memory only, never in a decoy session) and are offered back after the next unlock. A new
  recovery card does the same until its holder has typed part of it back (the server has
  already replaced the old card, so it is the only copy): it comes straight back after a
  real unlock within 10 minutes, never in a decoy session, and closing it unchecked asks
  first ("Close without saving your new card?").
- **Item · Viewer.** Every menu row says what it does. Save a copy asks for its own check,
  says the copy is unsealed, and is recorded in Activity (the fine print was true in 2.x
  only for Open and Delete).
- **Activity.** One line — "Verified on this phone ✓ · as of 2 min ago" — that expands to
  the details; no hex in rows; an event detail sheet names the chip proof in words.
- **You.** A hub of summary rows (Protection 2 of 3 · Devices · Recovery · Duress ·
  Heartbeat · Help others · Settings · About) that push detail screens. "Close HumID &
  erase vault" lives under About › Advanced, shows the document count, and asks for
  CLOSE to be typed before the live check. Witnesses can be added one at a time and a
  "Send the steps" message helps the friend. Heartbeat counts down in the vault server's
  time and says plainly that no signal means no heartbeat.
- **Connection.** The "can't reach your vault" strip is in the flow of the page, never
  over a title. Offline read-only works as in 2.x, with one thing 3.0 had to add because
  its screens load on demand: once the vault is open, the Activity and You screens' code
  is fetched in idle time (about 20 KB, after first paint), and the web app's service
  worker keeps every screen's code, so a connection that drops — or an installed web app
  opened with none — still shows Activity and You, read only. A screen whose code truly
  can't be fetched says "This screen needs a connection the first time" with Try again,
  never a blank page (`main.jsx` `chunk()`; `tests/browser/offline.mjs`).

## 4. Security changes in the client (3.0.0)

Each item names the review finding it answers (`docs/HARDENING.md` carries the full table).

| Change | Answers |
|---|---|
| A plaintext (unauthenticated) JSON error from the transport can no longer steer identity-level state: only `session_unknown`/`session_expired` are believed; anything else is a `transport_error` and the app never deletes its offline copy or shows a terminal "set up again" screen on it (`packages/htp/src/client.js`) | SEC-A-01 |
| The sealed duress setting is padded to a fixed size, a default is sealed at first unlock, and a missing setting on a device that once had one reads as tampering (fails toward the decoy) (`core/duress.js`) | SEC-A-02, SEC-A-14 |
| A session epoch: results that land after a lock are wiped, not shown (`core/runtime.js`, `vault.js`, `ledger.js`) | SEC-A-05 |
| A compiled server pin always wins over a stored one (`core/session.js`) | SEC-A-06 |
| Split keys ratchet: once a vault has said it splits keys, this HumID refuses to seal unsplit, whatever a later unauthenticated hint says (`core/vault.js`) | SEC-A-13 |
| Index entries are padded to 64-byte buckets before sealing, so a pin or a decoy flag changes nothing the server can measure (`@humid/crypto` 1.6.0; entries sealed by 2.x still open) | SEC-A-09 |
| Marking an item for the decoy view needs a live check (`core/vault.js setDecoy`) | SEC-A-15 |
| Save a copy needs its own check and is in the ledger | UX-25 |
| QR codes are read by the bundled zxing-cpp reader; `jsqr` (2020) is gone | SEC-A-25, PERF-13 |
| Duress default gesture is the triple-tap; the hold is 3 s | UX-13 |
| Location stamp opt-in, coarse by default, no altitude | SEC-A-18 |
| Every file under `/assets/` is content-hashed and immutable; the shell is `no-cache`; the service worker precaches by hash, so an installed PWA can't run a year-old `app.js` | SEC-A-26, PERF-12 |

**Not in 3.0.0, and where it goes** (each needs a server change or a native change):
SEC-A-03 (witness/anchor recovery must verify the share `owner` and show the match code
before `finishJoin`), SEC-A-04 (index AAD bound to account + object + revision; needs
`@humid/crypto` 2.0 and a vault migration), SEC-A-07 (raw-bytes IPC for the gate secret;
Swift/Kotlin/Rust), SEC-A-08 (equal post-unlock calls in decoy sessions), SEC-A-10/11
(60-bit match code; approval hold with veto), SEC-A-12 (strip `\p{Cf}` on Android),
SEC-A-16 (keep an unreadable pass), SEC-A-17 (pin the envelope signer: H-1), SEC-A-21
(export-compliance plist key), SEC-A-22/23 (clock offset, response caps), and every
server item in `review-security-server` (SEC-S-01 assertion binding first).

## 5. Weight, storage, battery

Measured on the release build (`node apps/mobile/build.mjs`, brotli at the edge):

| | 2.1.2 | 3.0.0 | Budget |
|---|---:|---:|---:|
| First-load JS, gzip (the app entry and every chunk it imports statically) | 199 KB | **98 KB** (86 KB brotli) | ≤ 120 KB |
| First-load CSS, gzip | 12.1 KB | **10.1 KB** | ≤ 10 KB |
| Fonts on first paint | 163–205 KB, 6 requests | **0** | 0 |
| Total first paint (JS + CSS + fonts, gzip) | ≈ 375–415 KB | **≈ 108 KB** | ≤ 170 KB |
| Installed web assets (Tauri `frontendDist`) | 11.48 MB | 11.39 MB (one SIMD OCR core instead of the plain one; the engines are the next step, below) | ≤ 1.5 MB once OCR is native |
| Idle CPU on Lock / Welcome / empty Vault | rAF starfield + 2 spins + live `drop-shadow` | **0 frames, 0 timers** | 0 |
| 1 Hz timers while unlocked, idle | 2–3 | **0** (a clock runs only in a leaf that counts down, and stops when hidden) | 0 |
| Camera during a photo | 4K | ~1080p ≤ 30 fps (guided: long side 1920, 2560 for a passport, never a crop; the photo is a separate still), track stopped when hidden | |
| OCR core | non-SIMD | SIMD when the WebView has it (≈ 2× faster per read) | |
| Join polling | 24 calls/min | unchanged (next: long-poll) | ≤ 6 |
| Storage per sealed item on device | < 1 KB | < 1 KB | |
| Service-worker cache | everything touched, re-fetched every deploy | the shell and every screen's code (hashed), not the scan engines; a deploy re-fetches only what changed | |

The OCR and barcode engines (≈ 9 MB installed) are still bundled: a phone can't be sure of
a network when someone scans an ID at a counter. The next step is native OCR and barcode
reading through the gate plugin (iOS Vision, Android ML Kit) with the WebAssembly engines
kept only for the web app, fetched lazily; that removes ≈ 9 MB from every install.
`npm run sizes` prints the table above for any build (`HUMID_META=1` writes the esbuild
metafile; `tools/sizes.mjs` reads the output directory). The edge image and the Windows
server build with `HUMID_PRECOMPRESS=1`, which writes `.br`/`.gz` siblings the edge serves
as-is; the native shells build without it, so an install never carries them.

## 6. The communication boundary

`core/comms/contract.js` is the whole contract for secure human-to-human communication
and the reason 3.0 can grow into it without a forklift. A message is a sealed envelope like
any document: sealed on the sender's phone to the recipient's HumID keys (ML-KEM-1024 +
X25519), signed by the sender's ML-DSA-87 key, with its key split so a copied phone opens
nothing; one live check seals, one live check opens; every send, open and delete is a
ledger event on both sides; the recipient is a HumID found through a match code, never a
phone number, email or name; a duress session sends and opens nothing real; arbitrary
payloads. Nothing in the app imports an implementation: screens and the kernel talk to
`comms`, and a transport (the HumID server's relay, a local link, a mesh) registers behind
it. In 3.0.0 no transport ships and the Messages surface is absent until one does.

## 7. What the reviews found (summary)

Four reviews were written against 2.1.2 before a line of 3.0 was built; the full texts
are in the HumID 3.0 project. In short:

- **UX (50 findings, 15 prioritised).** The core promise was never said in plain words;
  "check" meant four things; a grey primary button on the most important step; drafts
  lost on every lock; a default duress gesture a tremor could trigger; a catastrophic
  button 64 px from a daily one; a You tab carrying twelve cards; no real dynamic type.
  What was excellent and is kept: one vocabulary, the check overlay, the two-way match
  code, the recovery-card type-back, destructive-action safety, the document camera,
  per-field provenance, card handling, offline read-only, the lock-issue screens, the
  Heartbeat copy, the witness "call them first" rule, the accessibility foundations.
- **Security, client (26 findings; 1 High).** The High (a plaintext error steering
  identity state) and six Medium/Low items are fixed above; the rest are scheduled.
- **Security, server (23 findings; 1 High).** The High: internal assertions are not
  bound to method, path or body and are never checked for replay, so one captured
  step-up assertion authorises "delete everything" for 30 s. Not an app change; first in
  the server queue, with the IPv6 /64 limiter key, the 64 MB frame buffer, the inert
  attestation revocation list in Docker, the Heartbeat monotonic clock under suspend, the
  anchor oracle, fail-open lockdown, and plaintext Windows backups.
- **Performance (20 findings).** 81 % of the install is OCR; the lock screen was an
  animation loop; three always-on timers; 190 KB of add-flow code at first paint; 204 KB
  of fonts; 4K camera for 224 px analysis; unhashed immutable assets.
