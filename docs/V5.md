# HumID 5.0 — build specification

23 October 2026 · Parker Dunning · from the full code review of 23 October 2026.
Living copy with diagrams: the "HumID 5.0 — build specification" doc in the HumID 4.0 project.

HumID 5.0 is post-quantum from the ground up: every key that opens your data is made by a fresh hardware operation inside a live face or fingerprint check on your own device, combined with quantum-safe keys, so no server, operator, thief or future quantum computer can open it alone.

## The promise, precisely

No key that opens your data exists anywhere unless your own device's secure hardware has just performed an operation inside a live face or fingerprint check. The hardware does the work each time; it doesn't hand out a stored password.

| Who | What they can open in 5.0 |
| --- | --- |
| HumID, the server operator, or anyone who seizes the servers | Nothing. Servers hold ciphertext, one key share per document, and public keys. |
| A thief with your locked phone | Nothing. The keys stay in the secure chip and need your biometric. |
| A future quantum computer with years of recorded traffic and stolen data | Nothing. Every confidentiality path is ML-KEM-1024 hybrid or 256-bit symmetric. |
| Malware that copies memory once during an unlock | Only what was open at that moment. The stored wrap has already moved on; other documents each need a new hardware operation plus a server share released by a fresh live check. |
| Someone holding a copy of your account seed | Nothing on its own. A new device joins only with an existing device's live approval, or through recovery with its wait and veto. |

Limits, stated honestly (these belong in the app and the marketing too):

- While a document is open, its plaintext is on the screen and in memory. Malware with full control of the phone at that moment can read it.
- Someone can be forced to unlock. Duress mode and Check-in reduce the damage; nothing removes it.
- The biometric check is the phone's own (Face ID, Class 3 fingerprint). HumID proves an enrolled biometric matched on attested hardware; it does not detect liveness or spoofing beyond what the phone does.
- Hardened recovery is a second way in, by design: two of your proofs, a wait and a veto, but not your old device. Holder-only mode has no second way in: lose every device and the data is gone.

## At a glance

One live check drives two things at once. The secure chip unwraps the seed and makes this document's hardware output, and it signs a proof that makes the key-share service release one share. The document key combines the account secret (ML-KEM-1024 + X25519), the hardware output and the key share. The servers never hold enough to open anything.

## One crypto suite: HUMID-PQ2

One frozen suite, named in every stored object, transcript and AAD as `{suite, v}`. NIST-standardised throughout (FIPS 203, 204, 205); category 5 everyday.

| Job | Algorithm | Why |
| --- | --- | --- |
| Key exchange, everyday | ML-KEM-1024 + X25519; one combiner binding both secrets, both ciphertexts and both public keys | Quantum-safe with a classical backstop |
| Key exchange, vault root | Add HQC-256 once its NIST standard is final | Insurance against a lattice break |
| Signatures, everyday | ML-DSA-87, hedged | Category 5 |
| Signatures, long-lived roots (ledger and log checkpoints, release key, server identity, account-root changes) | ML-DSA-87 and SLH-DSA-SHA2-256s | Hash-based second signature |
| Live check from the secure chip | ECDSA P-256 and ML-DSA-87 where supported (iOS 26 Secure Enclave, Android 17 Keystore) | Hybrid at the moment of use |
| Encryption at rest | AES-256-GCM-SIV | Nonce-misuse resistant under long-lived keys |
| Encryption in transit | AES-256-GCM, counter nonces | |
| Key derivation | KMAC256, length-prefixed inputs | One Keccak family |
| Hash | SHA3-512 / SHAKE256 | |
| Outer TLS | TLS 1.3, X25519MLKEM768 required; SecP384r1MLKEM1024 where clients allow | |
| Internal TLS | TLS 1.3, SecP384r1MLKEM1024 only; ML-DSA certificates when supported; CA ≤ 2 years | No silent downgrade |
| Anonymous payment passes | RSA blind signatures, each long-lived use anchored in the ML-DSA log | Replace when a PQ scheme is standardised |
| Randomness | Platform CSPRNG only, including jitter | |

Implementations: native and constant-time wherever available (CryptoKit on iOS 26, BoringSSL/Conscrypt on Android, OpenSSL 3.5 or AWS-LC on servers). The JavaScript library stays only as a checked fallback. Every backend passes NIST known-answer tests and cross-checks (including randomness) before use.

## The device key: a hardware unlock that ratchets

Every unlock:

1. One biometric prompt (iOS: fresh context, no reuse window; Android: per-use key, no time window).
2. Inside that check the hardware computes this unlock's factor `HW_n`.
3. `K_wrap = KMAC256(HW_n ‖ ss_soft, "HUMID-PQ2 device-wrap" ‖ device ‖ n)`; `W_n` is opened with AES-256-GCM-SIV.
4. Material for unlock `n+1` is picked at once (targets public hardware keys or plain writes, so no second prompt).
5. The seed is re-wrapped as `W_{n+1}`; `W_n` is deleted.

| Platform | Hardware operation per unlock | Why it's quantum-safe |
| --- | --- | --- |
| Android (StrongBox, else TEE) | HMAC-SHA256 under a Keystore HMAC key: per-use biometric, invalidated by new enrolments, unlocked-device-only, attested | Purely symmetric, 256-bit |
| iOS 26+ | Secure Enclave ML-KEM-1024 decapsulation and Secure Enclave P-256 key agreement, one biometric context | ML-KEM inside the enclave |
| iOS before 26 | Secure Enclave P-256 key agreement combined with a 32-byte Keychain item (`.biometryCurrentSet`), rewritten every unlock | Breaking P-256 yields nothing without the enclave-protected item |
| macOS (Apple silicon) | As iOS | |
| Windows / Linux | TPM 2.0 HMAC key under policy | Lower assurance: the OS enforces the biometric |

`ss_soft` is an optional software ML-KEM-1024 + X25519 leg. Hardware outputs travel as bytes, never text, and are wiped. Verify on device that iOS 26 Secure Enclave ML-KEM keys accept biometric access control.

## Opening a document: three keys, all needed

`K_doc = KMAC256(ss_acct ‖ HW_doc ‖ share_ks, "HUMID-PQ2 doc" ‖ suite ‖ docId ‖ manifestHash)`

| Input | Where it comes from | Who can't produce it |
| --- | --- | --- |
| `ss_acct` | ML-KEM-1024 + X25519 decapsulation with the account key, inside the live check | The server, a thief, a quantum attacker |
| `HW_doc` | The device's hardware operation on a per-document input (one wrap per enrolled device) | Anyone without this device and your biometric |
| `share_ks` | Released only after a fresh hybrid live proof for this document, sealed to a one-time ML-KEM key on the phone | Malware with a copied seed; the vault alone |

Envelope signers are pinned to the account's ML-DSA key. Adding a device re-wraps `HW_doc` inside a live check on an existing device.

## The live check

- Bound to one exact request (method, path, body, session, sequence, device, single-use nonce, 60 s), as today.
- Hybrid signature: P-256 and ML-DSA-87 where the platform allows; algorithms stored per device; a policy date retires P-256-only devices. One prompt per check.
- Proven every time: iOS App Attest assertion per check; Android attestation re-verified on a schedule; revocation at every sign-in.
- Device joins need a live approval on an existing device (attested model + a code bound to both devices' keys) or completed recovery. Sign-up never adds a device to an existing account.
- Long-lived proof is logged: anything a live check vouches for that must stay provable for years is hashed into the holder's ML-DSA ledger and the public log.
- Wording: "approved with a live check on a verified phone", never "verified human".

## Servers and trust

- Own hardware in two geographically separate micro data centers with a live N+1 standby; nothing on a hyperscaler; no production server on a personal machine or tunnel.
- Server identity, ledger, release and seal keys in HSMs. No start in production without the seal key.
- Service statements and certificates move from Ed25519 to ML-DSA; internal TLS SecP384r1MLKEM1024 only, including inside one host.
- Split shares sealed phone-to-key-service in both directions.
- Every service re-verifies the holder's own live proof.
- Ledger and public log dual-signed (ML-DSA-87 + SLH-DSA); cosigner keys built into the app; at least one cosignature required; each account's ledger key pinned at creation in the public log.
- Signed, forward-only policy including registration mode, station lists and device policy; the app warns on unsafe server modes.
- Retention rule for every table, cap for every cache, always-rollback transactions, rate limits keyed to a verified client address.
- Windows server: dedicated service account, signed and encrypted backups, admin enrolment covering the liveness key, ML-DSA-signed updates.

## Recovery

| | Holder-only | Hardened |
| --- | --- | --- |
| What gets you back in | Another of your own enrolled devices | 2 of your proofs, then a wait every surviving device can veto |
| Lose every device | Data is gone; said plainly at setup | Recover on a new phone |
| Operator can help or hurt | Neither | Can't release anything without your proofs, the wait and no veto |

- No server-held piece counts as your proof: the passport piece is split between two independent key-share operators that release only after the wait. Until then the passport doesn't count as an independent proof.
- Pieces rotate automatically when a witness, card, chip or security key is removed.
- Witness shares sealed to ML-KEM-1024 keys; recovery cards ≥ 160 bits with a server-keyed lookup tag.
- FIDO hmac-secret uses a fresh salt per epoch.
- Classical identity proofs (passport chips, FIDO) are labelled and logged in the ML-DSA ledger when used; policy can stop counting them.
- A recovered phone enrols new hardware keys and re-wraps every document before opening anything.

## Messaging

- "Live" means the last 10 minutes: stamp keys rotate every ≤ 10 minutes; the receiver checks the epoch against its own receipt time.
- Stamp keys published in the cosigned public log and fetched anonymously (no per-account keys).
- Hybrid live stamp: blind RSA plus an ML-DSA signature from the sender's hardware liveness key, encrypted to the contact only.
- Stored conversations follow the vault rule: hardware-derived per-conversation keys, rotated per save, hardware rollback counter.
- One outbox state machine committed atomically with the ratchet; nothing deleted until read; a duress session sends nothing.
- Chunked history with per-chunk keys.
- Less metadata: prefix mailbox fetches, constant-rate cover polls, one size class for invites and requests, optional Tor/mixnet transport, blind post tokens per live check instead of IP quotas.
- Handshake, ratchet and live-stamp rule modelled in Tamarin or ProVerif before freeze.

## App architecture: keys in a native core, none in the UI

- One Rust core (`humid-core`) for iOS, Android and desktop holds the seed and does every wrap, unwrap, seal and open; secrets wiped on drop (`zeroize`, locked pages where allowed).
- The UI is secret-free: it receives only what is on screen.
- Native constant-time crypto in the core; crypto agility is one table in the core.
- Lock means gone: session state zeroed, viewers closed, secret-holding drafts dropped.
- Heavy work (hashing, chip secure messaging, OCR) off the main thread with one owner and a stop on every exit path.
- Narrow web view: no outside navigation, pinned server only, `freezePrototype`, no debug globals, screenshot protection everywhere.
- Native plugins validate input (NFC command allow-list, length limits, timeouts); destructive plugin calls need a live check.
- CI compiles Swift and Kotlin and runs emulator tests; a device-lab run before any release touching the gate.

## User experience rules

1. One prompt per action.
2. Nothing irreversible in one tap: hold-to-confirm, say what will be lost, undo window where possible.
3. Warnings come to you as notifications (Check-in, recovery attempts, new-device requests).
4. Plain words, one vocabulary; no promise the code doesn't keep.
5. Errors say what to do next, with a button that does it.
6. WCAG 2.2 AA (4.5:1 text), 44 px targets, full VoiceOver/TalkBack, reduced motion, an alternative to every press-and-hold; known assistive tools are trusted.
7. Secrets aren't copyable or capturable.
8. Decoy parity tested screen by screen in CI.
9. Under 1 s to the lock screen on a mid-range phone; no needless per-second redraws.

## Build, release and supply chain

- Two people for every change to main (GitHub Team/Pro, protected main and tags, required second reviewer, signed commits). Releases only from tags on main.
- Signing secrets in a protected `release` environment; signing in a job that runs no repository code; actions pinned; dependencies verified.
- Every artifact signed with an HSM-held ML-DSA-87 + SLH-DSA release key that apps and servers pin; Play hybrid ML-DSA signing as it rolls out.
- Provenance and SBOM for every artifact; images deployed by digest.
- Reproducible builds.
- On every PR: CodeQL, secret scanning, Scorecard, zizmor, dependency review, NIST KATs, ML-KEM timing test, fuzzing of every wire format.
- Leaked test keystore purged from history and tags before 5.0 work starts.
